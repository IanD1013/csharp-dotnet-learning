## 1. Refresher - What are Domains & Sub-Domains

> [观看本课](https://dometrain.com/take/course/deep-dive-domain-driven-design-ddd-2760775/refresher-what-are-domains-sub-domains-54855759/) · 4:56

### 总结

本课从领域驱动设计(DDD)的角度,对领域和子领域的定义做一次基础性的回顾。
它解释了领域如何代表应用程序所处理的特定问题空间和知识范围,以及把领域拆分为子领域如何帮助做出更好的战略决策,例如识别核心业务价值,与那些可以委托给第三方服务或推迟到未来开发的组成部分区分开来。

### 核心概念

- **领域(Domain)**:用户应用程序所针对的主题领域;应用逻辑围绕其展开的知识与活动范围。
- **逻辑边界(Logical Boundary)**:由领域专家、开发者和用户的共享知识所形成的空间,它界定了软件的范围。
- **子领域(Sub-domain)**:嵌套在更大领域之中的一个更小、更细分的领域,通常包含它自己特定的业务规则和专家知识。
- **战略分解(Strategic Decomposition)**:把一个大问题拆分成可管理的部分,以确定哪些区域需要定制开发、哪些可以委托出去的过程。

### 课程笔记

在完成全局事件风暴(big-picture event-storming)和流程建模会议之后,开发团队应当对问题空间有整体的理解,掌握一套具体的领域术语词汇,并清楚地看到必须强制执行的业务不变量。
这正是识别子领域的理想时机,即把大问题拆分成更小、更易管理的部分。

#### 定义领域

一般而言,领域被定义为一个活动或知识的范围。
在软件工程和领域驱动设计的语境中,这个定义被细化得更加具体。
领域是用户应用程序所针对的主题领域。
它代表应用逻辑围绕其展开的知识与活动范围。
这会形成一个由领域专家、开发者和用户的共享知识所构成的逻辑边界。

虽然像"心理学"这样的一般领域很宽泛,但软件领域往往非常细分。
例如,一个领域可能被具体限定为"健身房课程排期软件"。

#### 理解子领域

领域在本质上是递归的。
一个细分领域,比如健身房课程排期,本身就是某个更大领域(比如"健身软件"或"一般意义上的软件")的子领域。
反过来,即使是一个具体的领域,也可以进一步拆分为更多子领域。

例如,在健身房排期软件中,参与者设定并追踪一个目标(例如一个月内参加五次功能性训练课)的过程,可以被看作它自己的一个子领域。
这个细分区域有它自己特定的问题、业务规则和专家。

```text
software in general
  └─ fitness software
       └─ gym session scheduling software
            └─ participant goal setting & tracking
```

#### 分解的战略重要性

战略阶段的首要目标,是获得足够的领域知识,以便对软件的构建做出明智的决策。
通过识别子领域,组织可以在资源分配方面做出关键的选择:

1.  **委托(Delegation)**:识别出解决常见问题的子领域(例如支付处理或身份管理),可以让团队使用第三方服务或现有软件,而不是构建定制的解决方案。
2.  **优先级(Prioritization)**:某些子领域可能被认为与最小可行产品(MVP)无关,可以推迟。
3.  **聚焦(Focus)**:通过把领域拆分成更小的部分,团队可以把精力和预算集中在提供最大业务价值的核心区域上。

## 2. Identifying Sub-Domains

> [观看本课](https://dometrain.com/take/course/deep-dive-domain-driven-design-ddd-2760775/identifying-sub-domains-54855760/) · 8:34

### 总结

识别子领域,是基于特定的业务边界把复杂的业务领域分解为更小、可管理的逻辑单元的关键过程。
这种分解依赖于对领域的深入理解,而这种理解通常是通过事件风暴和流程建模等探索技术获得的。
通过分析语言上的语义差异、核心业务流程、专业知识领域、数据使用模式以及现有的组织结构,架构师可以识别出系统内部天然的断层线。
这些子领域提供了必要的结构,使软件实现与业务现实保持一致,尽管最终的边界往往涉及战略性的业务决策,而不是简单的一一对应。

### 核心概念

*   语义边界:识别不同区域中使用的独特业务词汇。
*   核心流程:让子领域与主要的业务流程和功能保持一致。
*   专业知识边界:根据特定的专业或业务知识领域对功能进行分组。
*   数据流与边界:观察特定数据集在哪里被最频繁地使用或被独占需要。
*   组织归属:利用现有的团队结构和职责来识别逻辑边界。

### 课程笔记

识别子领域是领域驱动设计战略阶段中的一个基础步骤。
这个过程始于对领域的彻底探索。
全局事件风暴和流程建模等技术,对于获得识别系统中某些部分与其他部分不同所需的直觉至关重要。
系统的某些部分可能处理的是常见的、已被解决的问题,而另一些部分则代表了业务独特的价值主张。
为了在实践中识别这些子领域,可以运用五个主要视角。

#### 语义边界

语义边界是通过观察领域中不同区域所使用的独特词汇和业务语言来识别的。
当不同部分之间的术语差异显著时,就表明存在一个概念边界。
在健身房排期系统中,"session"、"trainer"和"participant"等术语是开展健身课程的核心。
相反,"gym"、"subscription"和"admin"等术语与组织和运营方面相关。
这种区别暗示存在两个独立的子领域:Session Management 和 Gym Administration。

```text
+-----------------------+     +-----------------------+
| Session Management    |     | Gym Administration    |
|  session              |     |  gym                  |
|  trainer              |     |  subscription         |
|  participant          |     |  admin                |
+-----------------------+     +-----------------------+
```

#### 梳理核心流程

子领域往往与业务的核心流程保持一致。
一个子领域应当封装处理某个特定端到端流程所需的全部功能。
例如,参与者在课程中预订名额的流程暗示了一个 Reservation 子领域。
与此同时,管理员创建和管理健身房、房间和课程的流程暗示了一个 Facility Management 子领域。
每个子领域负责完成其相应流程所需的逻辑和数据。

#### 专业知识边界

组织内不同的专业知识领域往往会形成天然的子领域边界。
管理设施、房间容量和器材所需的专业知识,不同于设计训练计划或理解课程应如何为参与者开展所需的专业知识。
认识到这些不同的知识孤岛,可以帮助识别出 Gym Administration 子领域与 Training 或 Session Design 子领域的区别。

#### 数据流与边界

观察数据在整个系统中是如何被使用的,可以揭示子领域的边界。
如果某一组特定数据被领域的某一部分大量或独占地使用,那么这个区域很可能是子领域的候选。
在健身房的语境中,房间、教练和参与者的排期数据必须相互对照,以防止冲突。
这些数据对 Reservation 子领域至关重要。
相比之下,支付方式和账单明细主要与财务运营相关,这暗示存在一个独立的 Billing 子领域。

#### 组织归属

在处理现有系统或大型组织时,当前的团队结构及其职责可以指向子领域。
这在重新设计遗留单体系统时尤其有用。
例如,一个专注于用户留存和参与度的团队可能管理个人目标(例如一个月参加五次瑜伽课)之类的功能,这指向一个 User Retention 子领域。
另一个团队可能负责为教练和管理员提供仪表盘和反馈回路,这表明存在一个 Analytics 子领域。

## 3. Classifying Sub-Domains

> [观看本课](https://dometrain.com/take/course/deep-dive-domain-driven-design-ddd-2760775/classifying-sub-domains-54855761/) · 3:09

### 总结

把子领域划分为核心(Core)、支撑(Supporting)和通用(Generic)三类,是领域驱动设计战略阶段中一项至关重要的工作。
这种分类使组织能够识别其主要的价值驱动因素,把它们与必要但不具竞争力的工具性功能区分开来,并识别出最好用现成方案解决的行业标准问题。
通过对子领域进行分类,团队可以让技术投入与业务优先级保持一致,确保创新集中在能带来最显著竞争优势的地方。

### 核心概念

- **核心子领域(Core Sub-Domain)**:主要的业务差异化因素和收入驱动因素。
- **支撑子领域(Supporting Sub-Domain)**:支撑核心但缺乏竞争优势的必要功能。
- **通用子领域(Generic Sub-Domain)**:已有行业解决方案的标准业务问题。
- **竞争差异化(Competitive Differentiation)**:识别是什么让一项业务在市场中独一无二。
- **战略重要性(Strategic Importance)**:把管理层的关注度和业务焦点作为分类的指标。
- **成本效益(Cost Efficiency)**:根据子领域类型,评估是构建定制软件还是购买现成方案。

### 课程笔记

在识别出子领域之后,战略阶段的下一步是分类。
子领域被划分为 Core、Supporting 或 Generic,以便确定开发投入的优先级,并让技术实现与业务目标保持一致。

#### 核心子领域

Core 子领域代表组织的"摇钱树"。
它是系统中最关键的区域,需要最高程度的关注和创新。
如果一个子领域满足以下标准,它就被归类为 Core:

1. **差异化**:它提供独特的竞争优势,使该业务区别于市场上的其他业务。
2. **收入与增长**:它与业务的收入来源和长期增长直接相关。
3. **战略重要性**:它吸引了高级管理层和利益相关者的高度关注。
4. **业务焦点**:它是公司内部战略决策和创新工作的主要对象。

#### 支撑子领域

Supporting 子领域对系统的运作必不可少,但不提供竞争优势。
它们的特征是:

1. **实用性**:它们提供能增强应用体验的功能,但并不是该服务的独立卖点。
2. **标准方案**:它们可以使用标准实践和成熟技术来开发,实现时只需极少的创新。
3. **战略关注度低**:它们得不到与 Core 子领域同等程度的业务关注或战略讨论。

#### 通用子领域

Generic 子领域处理的是整个行业通用、被视为"已解决问题"的功能需求。

1. **行业标准**:该领域已被充分理解,并且已经被许多组织广泛实现过。
2. **无竞争优势**:定制实现不会带来业务优势;这项功能只是系统得以存在的一项必要条件。
3. **成本效益**:对于这些领域,使用现成方案通常比在内部开发该功能更高效。

## 4. Section Recap

> [观看本课](https://dometrain.com/take/course/deep-dive-domain-driven-design-ddd-2760775/section-recap-54855762/) · 1:29

### 总结

本课总结了在领域驱动设计战略阶段中对子领域的探索。
它回顾了在问题领域中识别逻辑空间、把它们分解为更小的单元,并根据它们对业务的战略价值进行分类的过程。
本课为战略设计的下一阶段做好铺垫:定义限界上下文(bounded context)和上下文映射(context mapping)。

### 核心概念

- **子领域识别(Subdomain Identification)**:把一个大的问题空间拆分成可管理的逻辑单元。
- **嵌套与粒度(Nesting and Granularity)**:子领域可以存在于其他领域之中,并且可以被进一步分解。
- **分类类型(Classification Types)**:把子领域归类为 Core、Supporting 或 Generic。
- **战略决策(Strategic Decision Making)**:利用分类来决定把创新和资源集中在哪里。
- **过渡到限界上下文(Transition to Bounded Contexts)**:从问题空间(子领域)转向解决方案空间(限界上下文)。

### 课程笔记

子领域代表在领域探索过程中识别出的问题空间内的逻辑划分。
这些空间往往高度专门化,可以嵌套在更宽泛的领域之中,也可以被进一步细分为更小、粒度更细的子领域。
识别这些边界是管理大型业务领域复杂性的关键一步。

一旦识别出子领域,就必须对它们进行分类,以指导战略投入和开发工作。
三种主要的分类是:

- **Core 子领域**:它们代表业务的主要创新和竞争优势。
  它们需要最多的关注和高质量的工程实践。
- **Supporting 子领域**:它们是业务运作所必需的,但不提供竞争优势。
  它们通常在内部开发,但对创新的关注少于 Core 子领域。
- **Generic 子领域**:它们是并非业务所特有的常见任务(例如身份管理或支付处理)。
  为了保持成本效益,它们通常由现成软件或外包服务来处理。

分类过程包括评估每个子领域的业务重要性、它在成本效益方面的潜力,以及它是否是战略决策的主要驱动因素。
这种分析确保资源被分配到能提供最大价值的地方。

本节讨论的技术提供了一个把领域分解为子领域的框架。
在通用语言、不变量和子领域都已定义之后,战略阶段将转向定义限界上下文并进行上下文映射,以构建技术解决方案。
