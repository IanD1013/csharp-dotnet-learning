## 1. Different types of testing

> [观看本课](https://dometrain.com/take/course/from-zero-to-hero-unit-testing-for-csharp-developers-2722824/different-types-of-testing-53926790/) · 7:15

### 总结

软件测试是指编写代码来验证应用的行为,即断言特定的输入会产生预期的输出。
本课探讨测试的层级结构:从单元测试开始(它通过 mock 外部依赖来隔离逻辑,以获得最快的速度),再延伸到组件测试、集成测试和端到端测试,这些测试验证更广泛的系统交互以及真实的基础设施。

### 核心概念

- **测试即验证**:编写代码来断言应用逻辑的行为符合预期。
- **单元测试**:在隔离的状态下测试最小的代码单元(方法或类)。
- **Mocking**:用假对象替换真实的 I/O 调用(API、数据库),以确保测试保持快速且不依赖环境。
- **组件测试**:比单元测试范围更广,但仍然保持与外部依赖隔离。
- **集成测试**:验证应用能否与其真实依赖(例如数据库或外部服务)正确协作。
- **端到端(E2E)测试**:从用户的视角,跨越所有涉及的服务和基础设施,测试整个系统流程。

### 课程笔记

测试从根本上说,就是编写代码来验证其他代码行为的过程。
一个测试会执行一段特定的逻辑(例如一个方法、一个服务或一个应用),并断言其结果与预期结果一致。
例如,一个用于把全名解析为名和姓的方法,可以通过提供特定的输入并验证返回的各个部分是否正确来进行测试。
如果断言失败,就说明出现了回归(regression),或者实现中存在缺陷。

#### Unit Testing and Mocking

单元测试关注应用中最小的可测试部分,通常是一个方法或一个类。
单元测试的一个决定性特征是排除真实的 I/O 操作。
任何外部依赖,例如网络 API、数据库或文件系统调用,都会被替换为一个"mock"或"fake"。

Mocking 让测试能够模拟某个依赖的行为,而无需承担搭建复杂环境的开销。
由于没有外部依赖,单元测试速度极快,可以频繁执行,常常作为持续开发工作流的一部分,在每次保存文件时运行测试。

#### Component and Integration Testing

组件测试(有时也称为功能测试或窄集成测试)与单元测试类似,但覆盖代码库中更广的范围。
虽然它测试的是系统中更大的一部分,但通常仍然保持与真实外部系统的隔离。

相比之下,集成测试会调用真实的依赖,以确保应用能与外部系统正确集成。
例如,一个针对 API 的集成测试可能会验证从 HTTP 请求到数据库记录创建的整个流程。
这些测试范围更广,通常需要一个正在运行的环境,或者借助 Docker 这类容器化工具按需启动依赖。

#### End-to-End and Specialized Testing

端到端(E2E)测试从用户的视角验证整个系统流程,常常跨越多个 API、数据库和消息总线。
一个 E2E 测试可能会在某个 API 中触发一个"create user"请求,然后验证该用户已被持久化,并且一条消息已成功发布并被下游服务消费。
由于需要延迟和超时来等待异步操作完成,这些测试通常更慢、更复杂。

除了这些类别,开发者还可能使用性能测试来验证应用的速度,以及使用快照测试(snapshot testing)进行专门的状态验证。
本课程主要关注单元测试,以确保应用中最小的单元是健壮的。

## 2. What is unit testing and why it's important?

> [观看本课](https://dometrain.com/take/course/from-zero-to-hero-unit-testing-for-csharp-developers-2722824/what-is-unit-testing-and-why-its-important-53926791/) · 1:30

### 总结

单元测试是 C# 开发中的一项基础实践,它通过隔离代码和 mock 依赖,提供快速的反馈循环。
通过在开发周期早期捕获 bug 并集成到自动化构建流水线中,单元测试可以防止代价高昂的生产错误,并确保系统的可靠性。

### 核心概念

* **快速反馈循环**:单元测试的执行时间非常短,让开发者几乎可以即时验证系统行为。
* **依赖隔离**:mock 依赖可以确保测试只关注被验证单元的逻辑。
* **降低成本**:在开发阶段发现 bug,比解决流入生产环境的问题要便宜得多。
* **CI/CD 集成**:单元测试在构建流水线中充当守门人;只要有一个失败,就会阻止可能有问题的代码被部署。
* **测试驱动开发(TDD)**:一种在实现代码之前先编写测试的实践,强调从一开始就重视可测试性。

### 课程笔记

单元测试是稳健测试策略的基础层。
它的主要威力来自它所建立的反馈循环。
由于单元测试的执行时间非常短,并且使用 mocking 来隔离外部依赖,开发者可以立即得到关于系统性能和正确性的反馈。
这种速度让 bug 能够在进入生产环境之前很久就被发现和解决,而在生产环境中,软件缺陷可能导致重大的经济损失。

在专业的软件工程中,尤其是在拥有大量用户的大型组织里,单元测试通常是强制性的。
这些测试被直接集成到构建流水线中。
如果某个单元测试失败,整个构建过程就会被中止。
这种自动化保障通过确保已知的回归或逻辑错误永远不会被部署,来保护客户和业务。

虽然核心关注点是在逻辑编写完成后对其进行验证,但也有一些实践者采用测试驱动开发(TDD)。
TDD 是一种在实际功能代码之前先编写测试用例的方法论。
虽然有些人认为这种做法过于极端,但它凸显了测试在软件开发生命周期中所扮演的关键角色。

所有这些要素(速度、隔离和自动化)构成了所谓测试金字塔的基础,测试金字塔是一个根据粒度和执行频率来组织不同类型软件测试的概念框架。

## 3. The testing pyramid

> [观看本课](https://dometrain.com/take/course/from-zero-to-hero-unit-testing-for-csharp-developers-2722824/the-testing-pyramid-53926793/) · 1:57

### 总结

测试金字塔是一种可视化技巧,用于界定软件项目中不同测试类型的重要性和数量。
它建立了一个层级结构:单元测试构成宽阔的基础,其上是集成测试,顶端是数量较少的端到端(E2E)测试。
这种结构在平衡各种测试策略的范围与执行成本的同时,确保了全面的覆盖。

### 核心概念

* **单元测试**:金字塔的基础,代表数量最多的测试,用于覆盖特定的代码场景。
* **集成测试**:中间层,覆盖比单元测试范围更大的更广泛场景,但总数更少。
* **端到端(E2E)测试**:顶层,关注应用的外部接口,测试数量最少。
* **测试分布**:一个健康的项目通常拥有比集成测试多得多的单元测试,以及比 E2E 测试更多的集成测试。

### 课程笔记

测试金字塔是一种可视化技巧,用于理解软件项目中不同测试类型的相对重要性和所需数量。
虽然存在带有额外层级的金字塔变体,但它从根本上由三个层级组成:单元测试、集成测试和端到端(E2E)测试。

```text
               /\
              /  \        End-to-End (E2E) Testing   ~15
             /----\
            /      \      Integration Testing        30-50
           /--------\
          /          \    Unit Testing               100+
         /____________\
```

#### Unit Testing

单元测试构成金字塔的基础。
它们占据最大的面积,因为它们代表了代码库中数量最多的测试。
开发者应当编写尽可能多的必要单元测试,以验证应用中每一种可能的场景和逻辑路径。
由于它们粒度细、速度快,它们为代码提供了主要的安全网。

#### Integration Testing

中间层由集成测试组成。
这些测试的范围比单元测试更广,在金字塔中的位置也更高,这反映出它们离原始代码更远,并且关注不同组件如何协同工作。
因此,项目通常需要的集成测试比单元测试少。

#### End-to-End (E2E) Testing

金字塔的顶端是端到端测试。
这些测试从使用者的视角验证应用,关注对外暴露的接口,例如 API 端点。
由于它们测试的是高层功能,总数要少得多。
例如,一个有五个端点的 CRUD API 可能只需要大约 15 个 E2E 测试(每个端点大约 2 到 3 个),而同一个项目可能有 30 到 50 个集成测试,以及远超 100 个的单元测试。

单元测试被视为最关键的一层,因为它全面的覆盖和基础性的地位,为防范回归和 bug 提供了最重要的保护。

## 4. Why should you write unit tests?

> [观看本课](https://dometrain.com/take/course/from-zero-to-hero-unit-testing-for-csharp-developers-2722824/why-should-you-write-unit-tests-53926794/) · 3:12

### 总结

单元测试是 C# 开发中的一项基础实践,它能确保软件的可靠性、降低长期成本并提升代码质量。
通过自动化地验证应用逻辑,开发者可以及早捕获 bug、通过描述性的测试名称提供活文档,并有信心地重构代码,最终防止代价高昂的生产故障和停机。

### 核心概念

* **自动化验证**:用快速、可重复的自动化测试取代手动 QA,以覆盖所有逻辑场景。
* **成本效益**:通过防止代价高昂的生产 bug 和停机,降低业务的长期成本。
* **活文档(Living Documentation)**:使用描述性的测试方法名来记录应用的行为。
* **设计质量**:通过遵循可测试性所需的设计模式来改进软件架构。
* **重构安全**:提供一张安全网,在代码被修改时立即发现回归。
* **合规**:满足代码覆盖率和部署就绪方面的行业标准。

### 课程笔记

对于现代软件开发来说,手动测试是不够的,因为在每次代码变更之后手动验证每一种可能的场景是不可能的。
单元测试提供了一种在开发工作流中快速、自动地验证逻辑的方式,确保变更不会引入回归。

从业务的角度看,单元测试是一项关键的节省成本的措施。
虽然需要在开发者时间上进行初始投入,但一个生产 bug 的成本(包括客户不满、潜在的停机以及紧急修复)远远超过编写测试的成本。
在开发期间捕获一个 bug,比解决一个由客户发现的、导致应用崩溃的问题要便宜得多。

单元测试也是一种文档形式。
通过为测试方法使用高度描述性的名称,开发者可以阅读测试套件来准确理解应用应该做什么。
这让代码库更易维护,也让新开发者更容易上手。

编写单元测试自然会带来更好的代码质量。
为了让代码可测试,开发者必须采用特定的架构技巧和模式。
这种关系正是测试驱动开发(TDD)的基础,在 TDD 中,测试先于实现代码编写,从一开始就推动更好的设计决策。

在许多专业环境中,尤其是在大型公司里,单元测试是一项强制要求。
这些组织通常会强制执行代码覆盖率指标,代码必须达到这些指标才能被合并或推送到生产环境。
这确保了应用在不断成长的过程中保持稳定。

归根结底,单元测试让开发者安心。
它们创造了一张安全网,让你可以有信心地重构;如果某个变更破坏了现有流程,测试会立即失败,准确指出逻辑在哪里被破坏。
